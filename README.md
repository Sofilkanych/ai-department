# AI-департамент: від ідеї до продакшену

Віртуальний IT-департамент на агентах Claude Code. Ти даєш ідею і ухвалюєш ключові рішення, а 16 агентів-ролей проводять проєкт через 8 етапів під керуванням оркестратора.


## Встановлення

Департамент — плагін Claude Code. Встанови один раз, і він буде доступний у кожній новій сесії й будь-якій теці.

У Claude Code (термінал або десктоп-застосунок, версія 2.1.275 і новіша) одна команда:

```
/plugin install ai-department --marketplace Sofilkanych/ai-department
```

Або двома кроками (працює і на старіших версіях):

```
/plugin marketplace add Sofilkanych/ai-department
/plugin install ai-department@ai-department
```

Після встановлення в уже відкритій сесії — `/reload-plugins`.

**Приватний репозиторій.** Claude Code клонує його з git-доступом, який уже є на твоєму комп'ютері, і токен ніде не питає. Тому потрібні право читання репозиторію і налаштований git: для HTTPS — `gh auth login`, потім `gh auth setup-git`; для SSH — ключ, доданий у GitHub.

**Оновлення.** Після нової версії в репозиторії: `/plugin` → Marketplaces → `ai-department` → Update marketplace (оновлює і плагін), потім `/reload-plugins`. Або з терміналу:

```bash
claude plugin update ai-department@ai-department
```

**Видалення:** `/plugin uninstall ai-department@ai-department`.

## Як запустити

Створи або відкрий теку для своїх проєктів, запусти в ній Claude Code і напиши:

```
/department хочу внутрішній сайт, де працівники бронюють переговорні
```

Проєкт з'явиться в цій теці: `projects/<slug>/`. Повна форма команди — `/ai-department:department`; знадобиться, якщо в тебе є інша команда `/department`.

На старті оркестратор спитає **режим участі**:

| Режим | Що це означає для тебе |
|---|---|
| `easy` | Агенти самі вирішують дрібне й зворотне, питають лише важливе, а все, що вирішили за тебе, показують списком на вето |
| `medium` | Питають про кожне справжнє рішення (рекомендовано) |
| `hard` | Допитують кожне припущення й показують компроміси |

Від режиму залежить лише кількість питань. Повнота не залежить: усі вимоги й критерії приймання покриваються за будь-якого режиму, а ворота G1–G3 не пропускаються ніколи.

Інші команди:

| Команда | Що робить |
|---|---|
| `/department <ідея>` | Новий проєкт |
| `/department <slug>` | Продовжити проєкт з місця зупинки |
| `/department статус` | Усі проєкти: етап і ворота |
| `/department <slug> з етапу N` | Повернутися на етап N |
| `/department табло` | Запустити табло для проєктів поточної теки |

## Табло

Живий офіс департаменту: вісім кімнат-етапів, за столами сидять боти-ролі, і видно, хто зараз працює, хто спить, хто закінчив, а хто чекає на тебе. Над офісом — рівні (етапи), XP і відсоток виконання, збоку — досягнення, таски по хвилях і журнал подій.

Найпростіше — попросити оркестратор: `/department табло`. Він запустить сервер у фоні для поточної теки.

Вручну (з робочої теки, де лежить `projects/`):

```bash
python3 -I ~/.claude/plugins/cache/ai-department/ai-department/*/skills/department/dashboard/server.py --root .
```

Відкрий <http://127.0.0.1:8787>. Без жодного проєкту можна подивитись демо: <http://127.0.0.1:8787/?demo>. Сервер слухає лише твій комп'ютер (127.0.0.1) і лише читає `projects/*/state.json` та `docs/04-tasks.json`. Сторінка оновлюється кожні 2 секунди. Якщо порт зайнятий — `--port 8788`.

| Стан бота | Як виглядає |
|---|---|
| працює | підстрибує, друкує, світиться антена, над головою — що саме робить |
| у черзі | не спить, роззирається |
| чекає на тебе | хитається, жовта бульбашка; у «Твоєму кабінеті» дзвенить дзвіночок |
| заблокований | трусить головою, червоний знак |
| готово | зелена галочка |
| ще не черга | спить, над ним «z» |

Імена ботів, кольори й досягнення задані на початку скрипту в `skills/department/dashboard/index.html` — їх легко змінити.

## Етапи й ролі

| # | Етап | Агенти | Що виходить | Рішення за тобою |
|---|---|---|---|---|
| 1 | Старт | **ти** + `brief-interviewer` | `01-brief.md` — бриф після інтерв'ю в три фази, вимоги R-xx | **G1** |
| 2 | Дослідження | `business-analyst` | `02-requirements.md` — історії US-xx, глосарій | |
| 3 | Вимоги | `system-analyst` → `ambiguity-hunter` → **ти** → `architect`, `ux-designer`, `security` → `critic`, `blind-acceptor` | специфікація з AC п'яти типів, вирішені двозначності, архітектура, ADR, екрани, безпека, критика узгодженості, звірка з брифом | **G2** |
| 4 | План | `qa-engineer` → `planner` | `04-test-plan.md` — кожен AC → тест; самодостатні таски в `docs/tasks/` і `04-tasks.json` | |
| 5 | Розробка | `test-author` ×N → `developer` ×N → `code-reviewer` | кожен таск в окремій копії: спершу падаючий тест, потім код, рев'ю, злиття в `main` | |
| 6 | Перевірка | `qa-engineer`, `security`, `blind-acceptor` | звіти тестування, безпеки, сліпого приймання | |
| 7 | Реліз | `devops`, `security` + **ти** | план релізу, аудит файлів розгортання → розгортання | **G3** |
| 8 | Експлуатація | `memory-keeper` | `PROJECT.md` з картою коду, уроки, нові ідеї | |

Оркестратор — це скіл `/department`, він працює в головній сесії. Окремим агентом він бути не може: у Claude Code агент не вміє викликати інших агентів. Тому й питання агентів до тебе передає оркестратор.

## Правила, на яких усе тримається

1. **Передача через файли.** Кожен етап залишає документ на диску. Наступний агент читає оригінал, а не переказ.
2. **Автор себе не перевіряє.** Специфікацію атакує `ambiguity-hunter`, пакет документів перевіряє `critic`, тест пише `test-author`, а код — `developer`; код перевіряє `code-reviewer`, продукт — `qa-engineer` і `security`, а відповідність ідеї — `blind-acceptor`, який бачить лише бриф.
3. **Спершу тест.** Тест має впасти з правильної причини ще до коду. Розробник тести не змінює ніколи: якщо тест суперечить вимозі, вирішує людина.
4. **Окремі копії.** Кожен таск розробляється у власній копії репозиторію (git worktree). В основну гілку `main` потрапляє лише код, що пройшов рев'ю і повний прогін тестів поверх свіжого `main`.
5. **Самодостатні таски.** У файлі таска вже лежать потрібні шматки документів із підписом джерела. Агенту не треба перечитувати всю специфікацію.
6. **Ворота — за людиною.** Бриф (G1), специфікацію (G2) і реліз (G3) затверджуєш ти. Жодна зовнішня дія без твого «так».
7. **Трасування.** Кожна вимога має номер, і цей номер проходить увесь ланцюжок: `R-01 → US-01 → FR-01 / AC-01.1 → рядок тест-плану → T-001 → коміт → рядок у звіті приймання`.
8. **Пам'ять.** Агенти між сесіями нічого не пам'ятають, тому все важливе записують у `PROJECT.md`, ADR і `lessons.md`.

## Структура

**Плагін** (цей репозиторій):

```
.
├── .claude-plugin/
│   ├── plugin.json        ← опис плагіна і версія
│   └── marketplace.json   ← репозиторій водночас є маркетплейсом
├── agents/                ← 16 ролей: що робить, що читає, що видає, що заборонено
└── skills/department/
    ├── SKILL.md           ← оркестратор /department
    ├── templates/         ← шаблони документів, які передають агенти
    ├── scripts/check_tasks.py ← перевірка плану: покриття вимог і тест-плану, хвилі, файли тасків
    └── dashboard/         ← табло: офіс з ботами, рівні, досягнення (server.py + index.html)
```

**Робоча тека** (там, де ти запускаєш `/department`):

```
.
├── projects/<slug>/       ← кожен проєкт окремо, зі своїм git (гілка main)
│   ├── state.json         ← етап, ворота, режим участі, хто зараз працює, історія
│   ├── docs/              ← бриф, вимоги, специфікація, ADR, тест-план, таски, звіти
│   ├── app/               ← код продукту
│   └── .worktrees/        ← тимчасові копії тасків під час розробки (не в git)
└── lessons.md             ← уроки після кожного проєкту цієї теки
```

## Що перенесено з плагіна sdd

Частину правил узято з плагіна `sdd` (версія 2.3.0) і переписано під наш формат документів. Агентів `sdd` департамент не викликає — усе живе в наших агентах:

| Що | Де в нас |
|---|---|
| Інтерв'ю в три фази з внутрішніми лінзами, режим участі easy / medium / hard, список припущень на вето | `brief-interviewer`, оркестратор |
| Пошук двозначностей: 8 класів, «де два інженери збудують різне», рішення або відкладення з власником і строком | `ambiguity-hunter` |
| П'ять обов'язкових типів AC і заборона технічних подробиць у критеріях приймання | `system-analyst` |
| Критик узгодженості з шістьма класами знахідок і правилом «цитуй або викидай» | `critic` |
| Самодостатні таски з підписами джерел і бюджетом контексту | `planner`, `templates/task.md`, `check_tasks.py` |
| Тест-план: кожен AC → тест із рівнем, реальні тимчасові залежності замість моків | `qa-engineer` (режим «тест-план») |
| Розробка через тести з окремим автором тестів, класифікацією першого прогону і сходами ескалації | `test-author`, `developer`, оркестратор |
| Паралельна розробка лише в окремих копіях репозиторію | оркестратор (етап 5) |
| Карта коду для наступних проєктів | `memory-keeper` |

## Як налаштовувати під себе

Зміни вносяться в цьому репозиторії, а не в кеші встановленого плагіна.

- **Змінити роль.** Відредагуй `agents/<агент>.md`. Кожен файл має однакові розділи: роль, вхід, вихід, як працює, коли готово, що заборонено, формат відповіді.
- **Додати роль.** Скопіюй найближчий файл, зміни `name` і `description`, а потім додай виклик (`ai-department:<агент>`) у потрібний етап у `skills/department/SKILL.md` і бота в `skills/department/dashboard/index.html`.
- **Змінити документ.** Шаблони лежать у `skills/department/templates/`. Якщо змінюєш нумерацію (R-, FR-, AC-, SEC-) чи розділи файлу таска, онови й `skills/department/scripts/check_tasks.py`.
- **Брендбук.** На старті оркестратор спитає, чи він є; шлях передається `ux-designer`.
- **Випустити нову версію.** Підніми `version` у `.claude-plugin/plugin.json` (1.0.0 → 1.0.1 для правок, 1.1.0 для нових можливостей), перевір `claude plugin validate .`, закоміть і запуш. Без зміни версії користувачі оновлення не отримають.

## Що варто знати

- **Сліпота `blind-acceptor`** тримається на інструкції, а не на технічній забороні: агент технічно може прочитати будь-який файл. У звіті він має чесно написати, якщо прочитав зайве.
- **Окремі копії тасків** потребують підготовки залежностей у кожній копії. Архітектор задає для цього швидку команду в таблиці «Команди».
- **Вартість.** Повний цикл середнього проєкту — це десятки викликів агентів. Перший прогін роби на маленькій ідеї і в режимі `easy` або `medium`.
- **Дозволи.** Під час розробки агенти часто пишуть файли й запускають команди. Якщо запити дозволів заважають, налаштуй їх для цієї теки в Claude Code. Розгортання й push лишай під підтвердженням.
- **Корпоративні дані.** Перш ніж давати агентам код чи дані МХП, перевір політику компанії щодо хмарних AI-сервісів.
