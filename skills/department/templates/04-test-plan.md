## 1. Рівні

Лише з цього словника. Рядок, що не стосується проєкту, познач «не застосовується».

| Рівень | Що перевіряє | Стратегія | Інструмент (з архітектури) |
|---|---|---|---|
| unit | Чиста логіка: правило, розрахунок, валідатор | У пам'яті, без зовнішніх залежностей | |
| integration | Модуль із реальною залежністю (база, кеш, черга) | Тимчасова справжня залежність на час тестів, не мок | |
| contract | Межа між учасниками: форма API чи події | Перевірка реальної форми проти домовленого контракту | |
| e2e | Повний сценарій критичної історії | Через справжню точку входу з тимчасовими залежностями | |
| load | NFR із числом | Лише коли є числовий NFR | |
| component | Компонент інтерфейсу окремо (лише якщо є інтерфейс) | Рендер у тестовій обв'язці, перевірка виводу й поведінки | |
| e2e-через-UI | Сценарій через справжній інтерфейс (лише якщо є інтерфейс) | Через відрендерений інтерфейс із тимчасовими залежностями | |
| visual | Порівняння з еталонним знімком (лише веб) | Падає на ненавмисну візуальну різницю | |

## 2. Покриття критеріїв приймання

Кожен AC зі специфікації — хоча б один рядок. Очікуваний результат — людськими словами, без кодів статусів і SQL.

| AC | Тип AC | Тест (за змістом) | Рівень | Між модулями | Очікуваний результат |
|---|---|---|---|---|---|
| AC-01.1 | успіх | {наприклад: бронювання вільної кімнати зберігається} | unit | ні | {бронювання збережене} |
| AC-01.1 | успіх | {людина бронює кімнату з календаря} | e2e-через-UI | так | {людина бачить підтвердження} |
| AC-01.2 | помилка | {бронювання в минулому відхиляється} | unit | ні | {відхилено, людина бачить причину} |
| AC-02.1 | доступ | {чуже бронювання не можна скасувати} | integration | ні | {відмовлено, бронювання ціле} |

Рядки з «Між модулями: так» планувальник віддає таску реєстрації або окремому e2e-таску в останній хвилі.
